# INT-001 — Integrar features y validar compatibilidad

Issue: [#36](https://github.com/jeffersonmejia/app-distribuidas/issues/36) · Responsable: Jefferson (`jeffersonmejia`)

## Alcance

Validar la compatibilidad de las features en `develop` una vez completadas sus dependencias. La integración por PR, los builds, las pruebas, cobertura y CodeQL corresponden a los workflows existentes; esta tarea revisa su resultado y no duplica esas ejecuciones.

## Criterios de aceptación

- [ ] El Quality Gate requerido pasó para el estado integrado en `develop`.
- [ ] Las features respetan límites Feature-First: usan APIs públicas y no crean dependencias internas ni ciclos.
- [ ] Las migraciones aplican desde una base vacía y Hibernate valida el esquema conforme a `docs/orm-code-first.md`.
- [ ] Rutas, DTOs, errores y permisos de UI/API son compatibles y respetan el contexto tenant de `docs/multitenancy.md`.
- [ ] Las incompatibilidades encontradas tienen corrección asignada al feature responsable; no quedan conflictos de integración pendientes.

## Verificación

### Evidencia del 22 de noviembre de 2026

- `develop` está en `22c47fb` y el árbol local integrado tiene el mismo contenido.
- El workflow **Quality Gate** terminó exitoso para `22c47fb`: 124 pruebas de backend, build y pruebas del frontend, cobertura diferencial y CodeQL Java/TypeScript. El ruleset activo `Protect develop` exige los cuatro checks; la API de code scanning no reporta alertas abiertas.
- Revisión de imports Java: no se encontraron dependencias entre features hacia paquetes internos; las dependencias cruzadas encontradas usan paquetes `api`.
- Maven local terminó con **124 pruebas, 0 fallos, 0 errores**. Testcontainers aplicó las 7 migraciones Flyway desde esquemas vacíos; las pruebas Spring Boot inicializaron Hibernate con `ddl-auto=validate`.
- Frontend local: build correcto; en la suite completa hubo 341 pruebas aprobadas y un fallo en `InventoryPage.test.tsx` por `getByText('Stock bajo')` con varios resultados. La prueba aislada pasó, así que el fallo es intermitente y requiere corregir la consulta de prueba. El workflow de `develop` para el commit revisado pasó.
- Contratos UI/API: CRM tiene adaptador HTTP real. Projects y Marketing tienen controladores REST, pero las fábricas del frontend siguen eligiendo repositorios mock por defecto y devuelven `service_unavailable` si `VITE_DATA_SOURCE=api`. Inventory, POS y Accounting tampoco tienen controladores HTTP; sus fábricas de frontend carecen de adaptadores API. Esto contradice los criterios de FRONT-004/005, que exigen consumir las APIs de cada feature. No definí rutas/DTOs nuevos porque las tareas backend no los especifican.

### Hallazgos que requieren decisión

1. Acordar si el MVP exige APIs HTTP y consumo real desde la UI para Inventory, POS y Accounting, y confirmar la exposición de Projects/Marketing. La implementación actual de FRONT-004/005 no cumple ese contrato integrado; no se deben inventar rutas ni DTOs.
2. Corregir el test intermitente de Inventory para que distinga la métrica KPI de las insignias de producto.

INT-001 permanece bloqueada hasta acordar el alcance HTTP anterior y asignar los cambios a los owners de cada feature. La existencia de mocks sirve para la demo local, pero no demuestra compatibilidad con las APIs del backend.

## Criterio de cierre

Se cumplen los criterios de compatibilidad, la evidencia del workflow está disponible y cualquier defecto pendiente queda fuera de esta tarea con responsable y seguimiento definidos. No cerrar ante fallos de aislamiento tenant o decisiones de negocio sin especificación.
