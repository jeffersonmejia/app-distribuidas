## 1. Contexto y evidencia

La revisión manual de seguridad registrada por Esteban (`EMLarco`) en `docs/tasks/SEC-001.md`, el 22 de noviembre de 2026, encontró campos de texto sin un límite explícito en backend y base de datos. Un actor autenticado y autorizado podría almacenar valores muy grandes y aumentar el consumo de memoria, almacenamiento y procesamiento.

Campos observados por la revisión:

| Feature | Campo / dato persistido | Tabla o agregado indicado por la revisión |
| --- | --- | --- |
| CRM | Nombre completo del cliente | `crm_customer.full_name` |
| Projects | Nombre y descripción del proyecto | Proyecto |
| Projects | Título de tarea | Tarea |
| Marketing | Nombre y descripción de campaña | Campaña |
| Marketing | Cuerpo HTML y texto de plantilla | Plantilla |

La lista debe contrastarse con las entidades, DTOs, adaptadores y migraciones actuales antes de editar. No ampliar el alcance a campos adicionales sin registrar por qué y obtener aprobación de Jefferson.

## 2. Objetivo

Aplicar límites máximos explícitos y consistentes en las entradas HTTP, validación del backend, persistencia JPA y restricciones PostgreSQL para los campos aprobados. Rechazar datos demasiado largos de forma segura y documentar la decisión, la migración y la verificación.

La implementación debe preservar el aislamiento tenant existente, los contratos públicos salvo el rechazo documentado de entradas inválidas y la política Code First de `docs/orm-code-first.md` junto con `docs/multitenancy.md`.

## 3. Alcance

### Incluido

- Confirmar los campos afectados contra el código y esquema actuales.
- Aplicar las decisiones aprobadas del apartado 4.
- Añadir validación de entrada en los límites HTTP y restricciones persistentes compatibles.
- Crear una migración Flyway nueva; nunca editar una migración aplicada.
- Mantener entidades/adaptadores en `infrastructure/persistence`; no exponer entidades JPA en APIs.
- Responder a entradas fuera de límite con el formato de error público ya establecido, sin incluir el contenido enviado ni datos internos.
- Añadir o actualizar pruebas pertinentes de validación, persistencia y compatibilidad.
- Registrar resultados y actualizar este documento y `docs/tasks/SEC-001.md` después de confirmar la corrección.

### Fuera de alcance

- Cambiar reglas de negocio, truncar silenciosamente texto o eliminar datos existentes.
- Cambiar permisos, membresías, RLS, contexto tenant o roles.
- Cambiar contratos de POS, precios, impuestos o el hallazgo informativo `SEC-001-H2`.
- Incorporar límites para campos no listados sin decisión de Jefferson.
- Usar SonarQube como gate de PR o requerir licencias/servicios pagos.
