# POS-002 — Registro transaccional de ventas

Issue: [#30](https://github.com/jeffersonmejia/app-distribuidas/issues/30) · Responsable: Bruce (`BruceRodri`)

## Lógica

1. Obtener actor y tenant desde autenticación y `TenantContext` ya validado; no confiar en IDs o permisos del cliente.
2. Validar la solicitud y consultar disponibilidad mediante el contrato público de Inventory.
3. Confirmar la venta y el movimiento de inventario de forma atómica: ambos persisten o ninguno. Si la API de Inventory no participa en la misma transacción local, no simular atomicidad; acordar un mecanismo consistente antes de implementar.
4. Devolver una venta confirmada solo después del commit. La falta de stock, un tenant inválido o una validación fallida no crea ventas parciales.

## Límites

POS es dueño de sus ventas y migraciones. No consulta tablas, entidades ni repositorios de Inventory. Usa UUID, tenant scope, restricciones PostgreSQL y migraciones Flyway. Dinero se representa con BigDecimal/NUMERIC; la precisión y reglas de precio deben provenir del contrato aprobado, no inventarse.

## Decisiones por cerrar

La regla de duplicidad requiere acordar una clave idempotente y su alcance. Confirmar también los campos de línea/importe y los códigos de error del contrato POS-001/INV-002 antes de fijar el esquema.

## Verificación

Cubrir venta exitosa, disponibilidad insuficiente, reintento duplicado, rollback, permisos y aislamiento por tenant. Issue #12 define el límite POS–Inventory; INV-002 concreta la API.
