# QA-006 — E2E Playwright para POS, inventario y CRM

Issue: [#204](https://github.com/jeffersonmejia/app-distribuidas/issues/204) · **Responsable:** Jennifer (`Jntorres2001`) · **Definición de alcance:** Jefferson (`jeffersonmejia`) · **Estado:** Todo, sin bloqueadores.

## 1. Contexto

El frontend tiene pruebas Vitest/Testing Library en `frontend/src/**`, pero no tiene Playwright ni pruebas E2E en navegador. Las pruebas actuales verifican componentes, páginas y adaptadores aislados; no demuestran los recorridos completos desde la UI hasta el backend.

`docs/testing.md` ya define como flujos críticos POS, consulta de disponibilidad de inventario y búsqueda/listado de CRM. Los cambios backend de esas features y sus pruebas de integración sirven de base. QA-003 conserva su alcance de integración/aislamiento tenant y QA-004 conserva sus mediciones k6; QA-006 no reemplaza ni duplica esos niveles.

El repositorio no incluye proveedor OIDC y el login del frontend sigue simulado en FRONT-003. Para ejecutar recorridos con backend real, esta tarea incorpora un proveedor OIDC efímero de pruebas local autorizado por Jefferson y usa solo usuarios, tenants y datos sintéticos aislados. No presenta el login simulado del frontend como una prueba de autenticación real.

## 2. Objetivo

Agregar Playwright como nivel separado de pruebas manuales/locales para verificar interacción visible, navegación y resultado integrado con el backend en los flujos POS, Inventario y CRM. Preservar las pruebas existentes de Vitest, integración backend, aislamiento tenant y rendimiento k6.

## 4. Flujos y criterios por recorrido

### POS — venta integrada

- Abrir el flujo POS, elegir un producto sintético disponible, completar el mínimo de datos sintéticos y confirmar la venta.
- Verificar confirmación visible para el usuario y, desde la UI de inventario o una consulta visible equivalente, el descuento esperado de existencias.
- Añadir un caso visible de rechazo/stock insuficiente solo si el estado se puede preparar de forma determinista sin duplicar las pruebas de reglas de dominio backend.

### Inventario — disponibilidad

- Consultar/listar o buscar un producto sintético en el backend real.
- Verificar que el nombre/estado y la disponibilidad devueltos se muestran correctamente, además del estado vacío o de error solo si es reproducible.

### CRM — búsqueda/listado

- Buscar/listar clientes sintéticos autorizados para el tenant de prueba.
- Verificar que el resultado coincide con los datos sembrados y que la UI muestra correctamente la ausencia de resultados.
- No usar nombres, correos ni datos reales.

## 5. No duplicar otros niveles

- No trasladar a Playwright pruebas de `codePointCount`, constraints Flyway, errores detallados de cada caso de uso, autorización granular o migraciones: permanecen en unitarias/integración backend.
- No repetir QA-003: Playwright puede comprobar el estado tenant-scoped visible del usuario sintético, pero la matriz positiva/negativa de aislamiento sigue en la integración backend de QA-003.
- No repetir QA-004: los umbrales de concurrencia, tasa de error y p95 de POS/inventario/CRM siguen siendo de k6.
- No crear asserts acoplados a detalles CSS/DOM; usar roles y nombres accesibles cuando la UI lo permita.

## 7. Seguridad y manejo del entorno

- Usar un tenant de prueba dedicado y una membresía `ACTIVE` asignada mediante el procedimiento administrativo documentado.
- La API sigue validando actor y membresía; un `tenant_id` desde la UI no sustituye la autorización backend.
- Los tokens/credenciales locales nunca se guardan en Git. Limitar su vida útil y no compartirlos en logs o reportes.
- No exponer Keycloak ni servicios del entorno QA a interfaces de red públicas. La instancia solo debe enlazarse a loopback/local.
- Las variables `VITE_*` son visibles para el browser y solo se usan con valores de prueba efímeros en modo desarrollo.
- El entorno es desechable sin tocar la base compartida; registrar claramente cómo iniciarlo, limpiar solo sus recursos propios y recrear sus fixtures.
